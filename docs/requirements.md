## 1. この資料について

- 決定した事項は「[3. 確定事項](#3-確定事項)」に移し、対応する Terraform 実装（モジュール・変数）を書く
- 未決事項は「[4. 未決事項一覧](#4-未決事項一覧)」に ID を付けて登録し、判断ポイントは「5. 未決事項の詳細」に書く
- 表の「暫定の推奨」は議論のたたき台であり、決定ではない
- 法定保存期間などの数値は、根拠条文を確認するまで「要確認」とする

**優先度の凡例**

| 優先度 | 意味 |
|---|---|
| A | 本番開始前に決定が必要 |
| B | 本番開始後に段階的に対応してよい |

## 2. 前提

| 項目 | 内容 |
|---|---|
| システム | 医用画像システム（PACS）と、RIS・電子カルテ等との連携 |
| 提供形態 | SaaS（複数医療機関、100施設以上を想定） |
| データ規模 | 画像 100TB/年以上 |
| 院内との接続 | インターネット + TLS のみ（VPN / Direct Connect なし） |
| 運用体制 | 自社のみ（保守の外部委託なし） |
| 準拠するガイドライン | 厚生労働省「医療情報システムの安全管理に関するガイドライン」第7.0版、総務省・経済産業省「医療情報を取り扱う情報システム・サービスの提供事業者における安全管理ガイドライン」第2.0版（詳細は [CLAUDE.md](../CLAUDE.md)） |

## 3. 確定事項

### 3.1 サービス・データ

| 項目 | 決定内容 | 設計への影響 | 実装状況 |
|---|---|---|---|
| 対象システム | PACS + 他システム連携（RIS / 電子カルテ等） | DICOMweb の受信口、将来 FHIR / HL7 連携の口 | 未実装 |
| 提供形態 | SaaS（複数医療機関、100施設以上を想定） | 総務省・経産省ガイドラインが主に適用。テナント単位のリソースは Terraform で個別管理せず、アプリのオンボーディング処理で動的に作成する。Terraform は基盤と権限の枠のみを持つ | 方針 |
| 院内接続 | インターネット + TLS のみ（VPN / Direct Connect なし） | 院内ゲートウェイ等から HTTPS（DICOMweb 等）で送信 | 未実装 |
| データ規模 | 大規模（画像 100TB/年以上） | 画像は S3 中心に保管 | 未実装 |
| 保存方針 | 階層化（直近は即時参照、以降は Glacier 系へ移行） | S3 Lifecycle（Standard → IA → Glacier 系） | 未実装 |
| アプリケーション | ECS 上で稼働。AWS HealthImaging の採用も検討 | 画像保管先を S3 直保存 / HealthImaging で差し替えられる構成にする | ECS は実装済み（`compute/ecs`）。画像保管は未実装 |

### 3.2 基盤・アカウント・DR

| 項目 | 決定内容 | 設計への影響 | 実装状況 |
|---|---|---|---|
| AWS アカウント | 環境（dev / stg / prod）ごとに別アカウント、AWS Organizations で管理 | 環境ごとに backend と provider を分離。`allowed_account_ids` で誤適用を防止 | 実装済み |
| リージョン | 国内リージョンに限定（主：ap-northeast-1、DR：ap-northeast-3） | `region`・`dr_region` を validation で国内に制限 | 実装済み |
| DR（暫定） | 大阪リージョン（ap-northeast-3）へのデータ複製を変数で ON/OFF | S3 クロスリージョンレプリケーション + AWS Backup クロスリージョンコピー | 一部実装済み（`dr_enabled`：CloudTrail ログ・ECR。画像・Backup は未実装） |

### 3.3 認証・運用体制

| 項目 | 決定内容 | 設計への影響 | 実装状況 |
|---|---|---|---|
| 利用者認証 | Cognito + MFA | `security/cognito`。パスワード要件は厚労省GL第7.0版 システム運用編14章に準拠 | 未実装 |
| 運用体制 | 自社のみ（保守の外部委託なし） | IAM Identity Center + MFA。踏み台は SSM Session Manager（SSH・公開 IP なし） | VPC エンドポイントのみ実装済み |
| コンテナへのログイン | ECS Exec は障害調査用。prod では使わない | セッションを KMS で暗号化し、操作内容を CloudWatch Logs に記録する。prod での有効化は validation で禁止 | 実装済み（`ecs_exec_enabled`） |

### 3.4 CI/CD（ECS デプロイ）

| 項目 | 決定内容 | 実装 |
|---|---|---|
| ツール | CodePipeline + CodeBuild | `cicd/pipeline` |
| ソース | CodeCommit（2025年11月に一般提供へ復帰）。各環境アカウントにミラーを置き、検証済みコミットを push して昇格する | `cicd/pipeline` |
| パイプライン / ECR | 各環境アカウントに個別に置き、環境ごとに再ビルドする。ベースイメージの digest 固定とロックファイルの使用で差分を抑える | `cicd/pipeline`・`compute/ecr` |
| タスク定義 | アプリリポジトリの `taskdef.json` から CI が登録する。Terraform はサービス・IAM・SG 等の土台だけを管理する | `compute/ecs`・`infra/cicd-templates` |
| デプロイ方式 | ECS ネイティブ Blue/Green（テストリスナーで確認、ベイク時間、自動ロールバック） | `compute/alb`・`compute/ecs` |
| ステージ順 | Source → Build → Approval（prod のみ）→ Migrate → Deploy。承認前に本番 DB を変更しない | `cicd/pipeline` |
| 本番承認 | 手動承認を必須とし、承認権限は承認者用の権限セットにだけ付与する（職務分離） | `cicd/pipeline`（`approver_policy_json`） |
| DB マイグレーション | パイプライン内で `run-task` で実行する。旧バージョンと互換のある変更（expand/contract）に限る | `infra/cicd-templates` |

### 3.5 環境ごとの設定方針

環境ごとの違いは `terraform.tfvars` の環境スイッチだけで吸収する。**【不可逆】** の設定は、一度 apply すると tfvars を戻しても元の状態に戻らない。

| 設定 | dev | stg | prod | 備考 |
|---|---|---|---|---|
| NAT・Interface エンドポイントの冗長化（`network_ha_enabled`） | 無効（1AZ に集約） | 有効 | 有効 | stg は本番同等の構成で検証する |
| 夜間・週末停止（`ecs_scheduled_stop_enabled`） | 有効 | 有効 | 無効（24時間稼働） | 平日 21:00〜8:00・土日はタスク数 0。祝日は対象外 |
| オートスケーリング（`ecs_autoscaling_enabled`） | 無効（1タスク固定） | 無効（2タスク固定） | 有効（CPU 使用率で2〜4タスク） | |
| Container Insights（`ecs_container_insights`） | 無効 | 有効 | 有効 | dev は費用優先 |
| ECS Exec（`ecs_exec_enabled`） | 有効 | 無効（必要時のみ一時的に有効） | 無効（有効化を禁止） | |
| ログの Object Lock（`s3_object_lock_enabled`） | 有効 | 有効 | 有効（無効化を禁止） | 【不可逆】 |
| CloudTrail ログの Object Lock モード・保持日数 | GOVERNANCE・30日 | GOVERNANCE・90日 | COMPLIANCE・1827日（暫定） | 【不可逆】prod は初回 apply 前に保持日数を確定させる（[U04](#u04)） |
| 大阪への複製（`dr_enabled`） | 無効 | 無効（DR 手順の検証時のみ有効） | 無効（RTO/RPO 確定後に有効化） | 【不可逆】（[U13](#u13)） |
| 本番承認ステージ（`pipeline_require_manual_approval`） | なし | なし | あり | |

## 5. 未決事項の詳細（判断ポイント）

### 5.1 契約・コンプライアンス

<a id="u01"></a>
#### U01 契約・コンプライアンス

**目的**：医療機関との契約と、ガイドラインが提供事業者に求める説明・合意の内容を固める。インフラの目標値（可用性・保存期間・DR）の多くはここから決まる。

| # | 論点 | 判断材料・選択肢 | 暫定の推奨 |
|---|---|---|---|
| 1 | SLA | 稼働率の目標、計画停止を稼働率の計算に含めるか、未達時の扱い | SLA を先に決め、SLO（[U15](#u15)）はそれより厳しくする |
| 2 | 責任分界表 | AWS・自社・医療機関（院内ゲートウェイ・端末・利用者管理）の役割分担 | 院内ゲートウェイ（[U07](#u07)）と利用者管理（[U08](#u08)）を含めて作る |
| 3 | ガイドラインが求める説明資料 | サービス仕様適合開示書、リスク評価の結果と対策の説明・合意 | セキュリティ概要ドキュメント（[U16](#u16)）を基礎資料にする |
| 4 | 第三者認証 | ISMS・ISMAP 等の取得の要否（医療機関の調達要件による） | 主要な顧客層の調達要件を確認してから判断する |

### 5.2 データ

<a id="u02"></a>
#### U02 テナント分離方式

**ガイドライン上の位置づけ**：共有 DB・共有スキーマ＋テナント識別子による論理分離は、3省2ガイドライン上禁止されていない。ただし次の条件を満たす必要がある。

1. 他テナントのデータを参照できないことを技術的に担保する（アプリの条件句のみに依存しない。例：PostgreSQL の RLS を強制する）
2. リスク評価の結果と対策を医療機関に説明し、合意する（総務省・経産省ガイドライン）
3. 契約終了時に、テナント単位でデータを返却・消去でき、その事実を証明できる

**候補（混合型）**：画像はテナント別の KMS キー／プレフィックスで分ける（キー削除による暗号学的消去が可能）。Aurora は共有スキーマ＋`tenant_id`＋RLS 強制とする。

> 条文番号は実装時に、厚労省GL第7.0版および総務省・経産省GL第2.0版の原文と照合すること。

<a id="u03"></a>
#### U03 データの保存期間・返却・消去

| # | 論点 | 判断材料・選択肢 | 暫定の推奨 |
|---|---|---|---|
| 1 | 保存期間 | 画像・レポート等の法定保存期間（要確認）と、契約上の保存期間。施設ごとに異なる期間を許すか | 法定期間を下限とし、契約で延長できる形にする |
| 2 | 保存階層の移行時期 | 即時参照が必要な期間（比較読影で過去画像を参照する頻度）と、Glacier 系に移す時期 | 施設の利用実態をヒアリングして決める |
| 3 | 契約終了時の返却 | 返却形式（DICOM ファイル一式、メタデータの形式）、受け渡し方法、期間 | 標準的な DICOM 形式で返却する |
| 4 | 消去と証明 | 消去の方法（オブジェクト削除 / テナント別キーの削除による暗号学的消去）、バックアップ・DR 複製からの消去、消去証明書の発行 | テナント分離方式（[U02](#u02)）と合わせて決める |

<a id="u04"></a>
#### U04 監査ログの保持期間

**現状**：prod の CloudTrail ログは暫定で5年（COMPLIANCE モード）。COMPLIANCE モードで書き込んだログは保持期限まで誰も削除できず、期間の短縮もできないため、**prod の初回 apply 前に確定が必要**。

| # | 論点 | 判断材料・選択肢 | 暫定の推奨 |
|---|---|---|---|
| 1 | 保持期間 | 法定保存期間（要確認）、契約上の要件、医療機関からの調査依頼に応えられる期間 | 契約（[U01](#u01)）と合わせて確定させる |
| 2 | 対象範囲 | CloudTrail 以外（VPC Flow Logs・ALB アクセスログ・アプリの閲覧履歴）も同じ期間にするか | 閲覧履歴（[U08](#u08)）は CloudTrail と同等以上にする |

<a id="u05"></a>
#### U05 既存 PACS からのデータ移行

| # | 論点 | 判断材料・選択肢 | 暫定の推奨 |
|---|---|---|---|
| 1 | 移行方式 | インターネット経由のオンライン転送 / AWS Snowball 等の物理媒体。施設ごとのデータ量と回線帯域で決まる | 施設ごとにデータ量を調べ、閾値を超える施設は物理媒体にする |
| 2 | 移行期間と二重運用 | 移行中に新しい検査が発生した場合の扱い、旧 PACS との並行稼働期間 | 新規検査は先に新システムへ切り替え、過去画像を後から移す |
| 3 | 移行データの検証 | 件数・ハッシュによる完全性の確認、移行記録の保存 | 移行記録を施設ごとに残す（説明責任のため） |
| 4 | 移行用の取り込み口 | 通常の受信口と分けるか（大量取り込みが通常業務の性能に影響しないように） | 分ける（[U22](#u22) の取り込み非同期化と合わせる） |

### 5.3 接続・連携

<a id="u06"></a>
#### U06 外部システム連携の方式

| # | 論点 | 判断材料・選択肢 | 暫定の推奨 |
|---|---|---|---|
| 1 | 連携方式 | FHIR API（HTTPS）/ HL7 v2（院内ゲートウェイが HTTPS に包んで送信）/ ファイル連携（SFTP 等） | 主要な顧客が使っている RIS・電子カルテの対応状況を調べて決める |
| 2 | 連携の向き | オーダー受信（RIS → PACS）、結果の返却（PACS → 電子カルテ）のどちらが必要か | 両方向を想定する |

<a id="u07"></a>
#### U07 院内ゲートウェイ

| # | 論点 | 判断材料・選択肢 | 暫定の推奨 |
|---|---|---|---|
| 1 | 提供・設置・保守の責任分界 | 自社が機器を提供するか、医療機関が用意するか。故障時の対応者 | 責任分界表（[U01](#u01)）に明記する |
| 2 | 機器認証 | mTLS（クライアント証明書）/ API キー / OAuth クライアント認証。証明書の発行・失効・更新の運用 | mTLS（漏えい時に機器単位で失効できる） |
| 3 | 送信元 IP の制限 | 施設の固定 IP で制限できるか（できない施設もある） | 可能な施設は制限し、機器認証を必須にする |

### 5.4 認証・認可

<a id="u08"></a>
#### U08 利用者ロール・ユーザー管理・閲覧履歴

| # | 論点 | 判断材料・選択肢 | 暫定の推奨 |
|---|---|---|---|
| 1 | ロール設計 | 読影医・技師・施設管理者・自社の運用者。他施設の画像を参照する場合（遠隔読影等）の扱い | まず施設内に閉じたロールを定義し、施設間の参照は別途検討する |
| 2 | ユーザー管理の委任 | 施設の管理者が自施設のユーザーを追加・削除できるようにするか | 委任する（退職者のアカウント削除を施設側で即時に行えるように） |
| 3 | セッション | セッションタイムアウト、端末の放置対策 | ガイドラインの要件を確認して決める |
| 4 | 閲覧履歴 | 誰が・いつ・どの患者の画像を見たかの記録、改ざん防止、保存期間、医療機関への提供方法 | アプリで記録し、改ざん防止付きのストレージに保存する（保存期間は [U04](#u04)） |

### 5.5 画像保管・配信

<a id="u09"></a>
#### U09 AWS HealthImaging の採用可否

| # | 論点 | 判断材料・選択肢 | 暫定の推奨 |
|---|---|---|---|
| 1 | 採用可否 | 画像保管・変換・配信をマネージドサービスに任せられる利点と、費用・機能の制約 | アプリの要件と費用を比較して決める |

### 5.8 監視

<a id="u15"></a>
#### U15 監視・通知（SLO 起点）

**目的**：利用者体験を基準にした目標（SLO）を定め、それを守れているかを測り、守れなくなりそうなときに通知する仕組みを作る。

**現状**：`monitoring` モジュールは未実装で、通知の仕組みはない。CloudTrail（CloudWatch Logs 連携）、ECS の Container Insights（stg・prod）、ALB のアクセスログ、CodeBuild のログ、ECS Exec の操作ログは取得している。

| # | 論点 | 判断材料・選択肢 | 暫定の推奨 |
|---|---|---|---|
| 1 | SLO の対象（どの利用者体験を守るか）と指標（SLI） | ビューアの画像表示（可用性・初回表示時間 p95）、DICOM 受信（成功率・取り込み完了までの遅延）、API 可用性 | まず「画像表示」と「DICOM 受信」の2つに絞る |
| 2 | 目標値と測定期間 | 例：可用性 99.9% / 30日。契約上の SLA との関係（SLO は SLA より厳しく設定する）。計画停止を含めるか | SLA を先に確認し、SLO はそれより一段厳しくする |
| 3 | 測定方法 | ALB メトリクス・ログ（サーバー側）、CloudWatch Synthetics（外形監視：利用者側から見た可用性）、アプリ計装（ADOT / X-Ray）、CloudWatch Application Signals の SLO 機能 | ALB メトリクス＋外形監視の併用。アプリ計装はアプリ側の方針と合わせて判断 |
| 4 | アラートの出し方 | エラーバジェットの消費速度（バーンレート）で通知するか、固定閾値で通知するか。即時対応（呼び出し）とチケット対応（翌営業日）の区別 | SLO はバーンレート、インフラ個別の異常は閾値。即時対応は SLO 違反の恐れがあるものに限る |
| 5 | 通知経路とオンコール体制 | SNS → Chatbot → Slack（monitor-alert）。自社のみの運用体制での夜間・休日の対応、エスカレーション手順 | Slack に集約し、即時対応分だけ電話・SMS 等の呼び出しを追加する |
| 6 | テナント単位の可視化 | 100施設以上のうち、特定の1施設だけで起きている障害（院内ゲートウェイの送信停止等）を検知できるか | 施設ごとの受信件数の途絶を検知する仕組みを検討する（アプリ側のメトリクスが必要） |
| 7 | 監視対象の範囲と通知チャンネル | ECS・ALB・Aurora・NAT・パイプラインの失敗に加え、セキュリティイベント（GuardDuty・Security Hub・root ログイン・IAM 変更等）。運用通知とセキュリティ通知を分けるか | チャンネルを分ける（セキュリティ通知は閲覧者を限定） |
| 8 | 障害時の医療機関への連絡 | 提供事業者ガイドラインが求める障害報告。インシデント対応手順との接続、ステータスページの要否 | 連絡基準（どの規模の障害を、いつまでに、誰へ）を先に決める |
| 9 | 保持期間とコスト | メトリクス・ログの保持期間、Synthetics の実行頻度、カスタムメトリクスの数 | 監査目的のログ（長期）と運用目的のメトリクス（短期）で保持期間を分ける |

## 6. 決定の依存関係と推奨順序

本番開始までに、次の順序で決めることを推奨する。前の段階の決定が、後の段階の前提になる。

| 段階 | 決めること | 理由 |
|---|---|---|
| 1. 契約とデータの方針 | U01 契約・コンプライアンス、U02 テナント分離、U03 保存期間・返却・消去、U04 監査ログ保持期間 | 可用性・保存期間・分離方式の目標値がここで決まる。U04 は prod の初回 apply 前に必要 |
| 2. アーキテクチャ | U06 外部連携、U07 院内ゲートウェイ、U08 ロール・閲覧履歴、U09 HealthImaging、U10 画像配信、U11 ドメイン、U12 ガバナンス | 段階1の方針を受けて、アプリ・インフラの構成を決める |
| 3. 非機能 | U13 DR、U14 バックアップ、U15 監視・通知、U16 セキュリティ概要 | SLA（U01）と構成（段階2）が決まってから目標値と仕組みを決める |
| 4. 運用準備 | U05 データ移行、U17 運用手順、U18 Terraform CI/CD、U19 テストデータ | 本番の構成が固まってから手順を作る |
| 5. 本番開始の判定 | U20 判定基準（U22 の初期規模の見積もりと負荷試験を含む） | 段階1〜4の完了を確認する |
| 本番開始後 | U21 CI/CD 暫定値、U22 スケールアップ計画、U23 コスト管理 | 運用実績を見ながら段階的に対応する |

**テーマ間の関係**

- **契約 → 非機能**：SLA（U01）が、SLO（U15）・DR の目標値（U13）・メンテナンスウィンドウ（U17）の前提になる
- **監視 → スケール**：SLO の目標値が、負荷試験の合格基準とスケールのきっかけになる
- **テナント分離 → データ・スケール**：テナント分離方式（U02）が、消去の方法（U03）・HealthImaging の採否（U09）・DB の拡張方法とセル分割の判断（U22）に影響する
- **監視 → セキュリティ**：監視で取るメトリクス・イベントが、セキュリティ課題（脅威検知・設定監査）の検知も兼ねる
