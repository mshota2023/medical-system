# S3 ストレージクラス選定 計画案

医用画像などを S3 に保存する際に、どのストレージクラスを使い、どう移行させるかを決めるための計画案。
東京リージョン（ap-northeast-1）を主、大阪リージョン（ap-northeast-3）を DR 先とする前提で、
コスト・改ざん防止・可用性などの観点からストレージクラスを比較する。

## 2. 前提条件

[requirements.md](./requirements.md) から、この計画に関係する前提を抜き出した。

| 項目 | 前提 |
|---|---|
| データ規模 | 画像 100TB/年以上 |
| 保存方針 | 階層化する（直近の画像はすぐ参照でき、それ以降は Glacier 系へ移す） |
| リージョン | 主：ap-northeast-1、DR：ap-northeast-3（国内に限定） |
| DR | 大阪へのデータ複製を `dr_enabled` で ON/OFF する。画像の複製はまだ実装していない |
| 画像保管先 | S3 に直接保存する構成と AWS HealthImaging を差し替えられるようにする（[U09](./requirements.md#u09)） |
| 既存の実装 | CloudTrail ログバケットで、Object Lock とライフサイクルによる GLACIER（Flexible Retrieval）への移行をすでに使っている（`modules/logging/cloudtrail`） |

## 3. ストレージクラス比較

### 3.1 コスト（東京リージョン・概算）

| クラス | 保存料金 (GB/月) | 取り出し料金 (GB) | PUT等 (1,000件) | GET (1,000件) | 最低保存期間 | 最小課金サイズ |
|---|---|---|---|---|---|---|
| S3 Standard | 約 $0.025 | なし | 約 $0.0047 | 約 $0.00037 | なし | なし |
| Intelligent-Tiering | 約 $0.025〜$0.002（アクセス状況で自動的に階層が変わる）＋ 監視料 約 $0.0025/1,000オブジェクト/月 | なし | Standard と同等 | Standard と同等 | なし | 128KB 未満は監視対象外で、常に高頻度アクセス層 |
| Standard-IA | 約 $0.0138 | 約 $0.01 | 約 $0.01 | 約 $0.001 | 30日 | 128KB |
| One Zone-IA | 約 $0.011 | 約 $0.01 | 約 $0.01 | 約 $0.001 | 30日 | 128KB |
| Glacier Instant Retrieval | 約 $0.005 | 約 $0.03 | 約 $0.02 | 約 $0.01 | 90日 | 128KB |
| Glacier Flexible Retrieval | 約 $0.0045 | 迅速：高め / 標準：約 $0.01 / 大容量：無料 | 約 $0.03〜 | 復元が必要 | 90日 | オブジェクトごとにメタデータ 40KB 分を追加で課金 |
| Glacier Deep Archive | 約 $0.002 | 標準：約 $0.02 / 大容量：約 $0.0025 | 約 $0.05〜 | 復元が必要 | 180日 | オブジェクトごとにメタデータ 40KB 分を追加で課金 |
| Express One Zone | 最も高い（Standard の数倍） | なし | 安い | 安い | なし | なし |

補足：

- 最低保存期間より前に削除・移行すると、残りの期間分の保存料金がかかる（早期削除料金）
- ライフサイクルで移行するときも、移行先クラスの PUT 料金がオブジェクト単位でかかる。**オブジェクト数が多いと、移行料金が保存料金の差額を打ち消すことがある**

### 3.2 性能・可用性

| クラス | 保存する AZ | 設計上の可用性 | 最初の1バイトが返るまで | 復元操作 |
|---|---|---|---|---|
| Standard | 3AZ 以上 | 99.99% | ミリ秒 | 不要 |
| Intelligent-Tiering | 3AZ 以上 | 99.9% | ミリ秒（任意で有効にする Archive 層は分〜時間） | 任意の Archive 層だけ必要 |
| Standard-IA | 3AZ 以上 | 99.9% | ミリ秒 | 不要 |
| One Zone-IA | **1AZ** | 99.5% | ミリ秒 | 不要 |
| Glacier Instant Retrieval | 3AZ 以上 | 99.9% | ミリ秒 | 不要 |
| Glacier Flexible Retrieval | 3AZ 以上 | 99.99% | 迅速 1〜5分 / 標準 3〜5時間 / 大容量 5〜12時間 | **必要** |
| Glacier Deep Archive | 3AZ 以上 | 99.99% | 標準 12時間以内 / 大容量 48時間以内 | **必要** |
| Express One Zone | **1AZ** | 99.95% | 1桁ミリ秒 | 不要 |

耐久性はどのクラスも 99.999999999%（イレブンナイン）として設計されている。ただし 1AZ のクラスは、その AZ が失われるとデータも失われる。

### 3.3 改ざん防止・セキュリティ

| クラス | Object Lock | バージョニング / MFA Delete | レプリケーション（大阪への CRR 等） | KMS 暗号化 |
|---|---|---|---|---|
| Standard / Intelligent-Tiering / Standard-IA / One Zone-IA / Glacier 3種 | ○（ライフサイクルで移行してもロックは引き継がれる） | ○ | ○ | ○ |
| Express One Zone（ディレクトリバケット） | **×** | **×** | **×** | ○（SSE-KMS） |

Object Lock・バージョニング・レプリケーションは、ストレージクラスではなく**汎用バケット**の機能である。
そのため Express One Zone 以外であれば、どのクラスでも Object Lock（COMPLIANCE モード）と長期保存を組み合わせられる。

### 3.4 3省2ガイドラインとの整合

| クラス | 医療情報の主な保存先にできるか | 理由 |
|---|---|---|
| Standard / Intelligent-Tiering / Standard-IA / Glacier 3種 | ○ | 複数 AZ に保存され、国内リージョンに置けて、Object Lock も使える |
| One Zone-IA | △（作り直せる二次データに限る） | 1AZ のため、BCP の観点で主な保存先には向かない |
| Express One Zone | ×（一時的な処理用に限る） | 改ざん防止・バージョニング・レプリケーションを使えない |

## 4. 選定に使う観点

コストと改ざん防止に加えて、以下の観点で判断する。

| # | 観点 | 確認すること |
|---|---|---|
| 1 | 最低保存期間と早期削除料金 | すぐ削除・移行するデータを IA や Glacier 系に置いていないか |
| 2 | 最小課金サイズとオブジェクト数 | DICOM のように小さいファイルが大量にある場合、128KB の最小課金、Intelligent-Tiering の監視料、移行時の PUT 料金がどれだけ効くか |
| 3 | 取り出し時間と業務上の RTO | 比較読影で過去画像を「すぐ見たい」のか、DR 時に取り出せればよいのか |
| 4 | 最悪ケースの取り出し料金 | DR 切替や他システムへの移行で全量を取り出すと、いくらかかるか |
| 5 | AZ 冗長性と可用性 | BCP の要件を満たすか |
| 6 | Object Lock・バージョニング・レプリケーション | 改ざん防止と DR 複製を組み合わせられるか |
| 7 | 国内で完結する DR | 大阪への CRR で越境移転なしに冗長化できるか。複製先のクラスをどうするか |
| 8 | 法定保存期間との対応 | 保存期間（[U03](./requirements.md#u03)）を、どのクラスに何年置くか・Object Lock の期間に落とし込めるか |
| 9 | 運用の手間 | 復元操作が必要か。アプリが復元待ちを扱えるか |
| 10 | 長期の総コスト | 5年程度の総コストで比べたときにどの構成が安いか（[6章](#6-概算コスト試算)） |

## 5. 計画案

### 5.1 データ種別ごとの割り当て

| データ | 推奨クラス・移行 | Object Lock | 理由 |
|---|---|---|---|
| 医用画像（主） | Standard → 一定期間後に Glacier Instant Retrieval | COMPLIANCE（期間は U03 で確定） | 過去画像の比較読影ですぐ取り出せる必要がある。取り出しがまれになった画像は Glacier IR で保存料金を約 1/5 にできる |
| 医用画像（大阪の DR 複製） | CRR で複製し、複製先は Glacier Deep Archive | 複製元と同じ | DR 時にだけ取り出すため、取り出しに時間がかかっても許容できる。保存料金が最も安い |
| 監査ログ（CloudTrail 等） | 現状のまま（Standard → GLACIER（Flexible Retrieval）） | COMPLIANCE（[U04](./requirements.md#u04)） | 実装済み。調査依頼のときに数時間で取り出せればよい |
| アクセスログ等の運用ログ | Standard → Standard-IA または Glacier 系 → 期限で削除 | 必要に応じて | 参照はまれ。保存期間が短ければ、最低保存期間に注意する |
| 一時ファイル（変換中の画像等） | Standard（短い期限で削除） | なし | 最低保存期間のあるクラスは使わない |

Intelligent-Tiering は「どれくらい参照されるかが読めない」場合の候補にとどめる。
画像のようにオブジェクト数が多いと、監視料が大きくなる（[6章](#6-概算コスト試算)）。

### 5.2 Standard から Glacier IR へ移す時期

- 施設へのヒアリングで、過去画像の比較読影に使う期間を確認して決める（[U03](./requirements.md#u03) 項目2）
- 決まるまでは暫定で **1年後に移す** とし、日数は変数で変えられるようにする
- Glacier IR は最低保存期間が90日のため、移行日数を短くしすぎないようにする

### 5.3 改ざん防止と削除

- 画像バケットは、作成時にバージョニングと Object Lock を有効にする（後から有効化できない設定や、モードを変えられない制約があるため、prod の初回 apply 前に方針を確定する）
- COMPLIANCE モードの保持期間は、保持期限まで誰も短縮・削除できない。U03 の保存期間が決まるまで、dev・stg は GOVERNANCE モードで検証する
- 契約終了時の消去は、テナント別の KMS キーを削除する暗号学的消去と組み合わせる（[U02](./requirements.md#u02)・U03 項目4）。Object Lock の保持期間中はオブジェクトを削除できないため、両者の期間の関係を整理する

### 5.4 暗号化・アクセス

- SSE-KMS（テナント別のカスタマー管理キー）で暗号化し、S3 バケットキーを有効にして KMS のリクエスト料金を抑える
- バケットポリシーで `aws:SecureTransport=false` を拒否し、パブリックアクセスブロックを有効にする
- 大阪への複製先でも同じ設定にし、大阪側の KMS キーで再暗号化する

## 6. 概算コスト試算

### 6.1 前提

- 毎年 100TB ずつ増え、5年間保存する（5年間の延べ保存量 = 15,000 TB・月）
- 1オブジェクトあたり平均 0.5MB（DICOM のインスタンス単位で保存する場合）とすると、年 2億オブジェクトになる
- 1TB = 1,000GB とし、料金は[3.1](#31-コスト東京リージョン概算)の概算値を使う
- 取り出し料金・データ転送料金（配信）・リクエスト料金のうち移行以外は含めない

### 6.2 構成別の5年間の保存料金（東京のみ）

| 構成 | 保存料金 | 移行・監視の料金 | 合計（概算） |
|---|---|---|---|
| A. 全量 Standard | 約 $375,000 | なし | 約 $375,000 |
| B. Standard 1年 → Glacier IR（推奨案） | 約 $183,000（Standard 5,400 TB・月 + Glacier IR 9,600 TB・月） | 移行の PUT 料金 約 $4,000/年 × 4年 ≒ 約 $16,000 | 約 $199,000 |
| C. Intelligent-Tiering（Archive Instant 層まで自動移行） | B と同程度 | 監視料 約 $75,000（延べ 300億オブジェクト・月） | 約 $260,000 |

### 6.3 大阪への DR 複製を追加した場合

| 項目 | 概算 | 備考 |
|---|---|---|
| Deep Archive の保存料金 | 約 $30,000（5年） | 大阪の料金は要確認 |
| リージョン間のデータ転送料金 | 約 $45,000（500TB × 約 $0.09/GB） | 転送単価は要確認 |
| 複製先での PUT 料金 | 約 $10,000/年 | Deep Archive の PUT 単価が高いため、オブジェクト数に比例して増える |

#### ストレージクラスと複製費用の関係

リージョン間の転送料金（GB 単価）は、ストレージクラスでは変わらない。東京から大阪へ送ったデータ量に、同じ単価がかかる。
ただし、複製全体の費用は複製元・複製先のクラスによって変わる。

| 費用 | クラスの影響 | 内容 |
|---|---|---|
| リージョン間の転送料金 | なし | 送ったデータ量 × 東京→大阪の単価（要確認） |
| 大阪側の PUT 料金 | あり（複製先のクラス） | 複製先クラスの PUT 単価で課金される。Deep Archive は単価が高い |
| 大阪側の保存料金 | あり（複製先のクラス） | Deep Archive が最も安い |
| 東京側の取り出し料金 | あり（複製元のクラス） | 新しいオブジェクトはアップロード直後（Standard のうち）に複製されるため、かからない。IA・Glacier IR に移ったあとの既存データを S3 Batch Replication で複製すると、取り出し料金がかかる |
| Glacier Flexible Retrieval / Deep Archive にある既存データ | あり | そのままでは複製できず、先に復元（料金と時間がかかる）が必要（要確認） |
| Replication Time Control（任意） | なし | 使う場合、GB あたりの追加料金がかかる |
| KMS | なし | 暗号化・復号のリクエスト料金がかかる。S3 バケットキーで抑えられる |

このため、以下の方針とする。

- 画像バケットを作る時点で大阪への複製を設定し、アップロード直後に複製されるようにする。あとから有効にすると、既存データの取り出し料金や復元が必要になる
- オブジェクトをまとめて保存しても、転送料金（GB 単価）は下がらない。下がるのは PUT 料金だけである
- AWS Backup で大阪へコピーする方式は、料金体系が異なる（バックアップ用の保存料金で、S3 の Deep Archive より高い）。100TB/年規模では S3 の複製のほうが安くなる見込みである（[U14](./requirements.md#u14) で比較して決める）

### 6.4 試算からわかること

- 構成 B は A の約半分になる
- **オブジェクト数が料金を大きく左右する**。インスタンス単位（1枚ずつ）ではなく、シリーズ・検査単位でまとめて保存すると、移行・複製・監視の料金を大きく減らせる。ただしビューアの部分取得（Range GET）や HealthImaging の採用（U09）と合わせて決める必要がある
- Intelligent-Tiering は、オブジェクト数が多いこの用途では監視料のため割高になる

## 8. 実装ステップ

1. 料金を公式ページと照合し、[6章](#6-概算コスト試算)の試算を更新する
2. 未決事項 1〜5 を決める（少なくとも保存期間と Object Lock の方針は、prod の初回 apply 前に必要）
3. 画像バケット用の Terraform モジュールを追加する。配置するカテゴリは CLAUDE.md の規約に沿って決める（既存の `modules/logging/cloudtrail` のバケット・Object Lock・ライフサイクル・CRR の実装を参考にする）
4. Glacier IR へ移す日数・Object Lock のモード・期間・DR 複製の ON/OFF を変数にし、環境ごとの値は `terraform.tfvars` で指定する
5. dev で GOVERNANCE モードを使って移行・複製・取り出しを検証し、stg で DR 訓練（大阪の Deep Archive からの復元）を行う
6. [README.md](../infra/README.md) のアーキテクチャとディレクトリ構成を更新する
