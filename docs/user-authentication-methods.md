## 1. この資料について

- 対象は、利用者（医師・技師・施設の職員等）が Web ブラウザやアプリからサービスにログインするときの認証。インフラ管理者の AWS アクセスや、院内ゲートウェイ等の機器認証は対象外（機器認証は要件定義の [U07](./requirements.md#u07) を参照）
- 本サービスの利用者認証は Cognito + MFA に決まっている（[要件定義 3.3](./requirements.md#33-認証運用体制)）。6章で各方式を Cognito で実現する方法をまとめた
- 調査日は 2026-10-16。Cognito の機能・プランは変わることがあるため、実装時に AWS の公式ドキュメントを確認する

## 2. 認証の基本

### 2.1 認証の3要素

| 要素 | 内容 | 例 |
|---|---|---|
| 知識 | 本人だけが知っている情報 | パスワード、PIN |
| 所持 | 本人だけが持っている物 | スマートフォン（認証アプリ・SMS）、セキュリティキー、IC カード、クライアント証明書 |
| 生体 | 本人の身体的特徴 | 指紋、顔 |

多要素認証（MFA）は、異なる種類の要素を2つ以上組み合わせる方式。パスワードを2つ使うなど、同じ種類の要素を重ねても MFA にはならない。

### 2.2 ID を誰が管理するか

| 方式 | ID の管理者 | 内容 |
|---|---|---|
| サービス独自のアカウント | サービス事業者 | サービス側でアカウントとパスワードを管理する |
| フェデレーション（SSO） | 利用組織（医療機関） | 医療機関の Microsoft Entra ID・Google Workspace 等でログインする。サービスは認証結果を受け取るだけ |
| ソーシャルログイン | 個人 | 個人の Google アカウント・Microsoft アカウント等でログインする |

## 3. 認証方式の概要

### 3.1 ID・パスワード

- 最も一般的な方式。単独では「知識」の1要素のみ
- 漏えい・使い回し・推測・フィッシングに弱いため、MFA との併用が前提になる
- 総当たり攻撃への対策として、一定回数失敗したらログインを一時的に止める（アカウントロック）

### 3.2 MFA の2要素目

| 方式 | 内容 | 注意点 |
|---|---|---|
| SMS ワンタイムコード | 登録した電話番号に SMS でコードを送る | SIM スワップ・SMS の傍受・フィッシングに弱い。送信費用がかかる |
| メールワンタイムコード | 登録したメールアドレスにコードを送る | メールアカウントが乗っ取られると突破される。パスワードと同じ端末で受け取ると「所持」の意味が薄れる |
| TOTP（認証アプリ） | Google Authenticator・Microsoft Authenticator 等のアプリが 30 秒ごとにコードを生成する | 通信不要で安価。フィッシングサイトにコードを入力させる攻撃は防げない |
| プッシュ通知 | スマートフォンのアプリに通知が届き、承認する | 承認を連打させる攻撃（MFA 疲労攻撃）に注意。番号照合で対策する |
| FIDO2 セキュリティキー | USB・NFC の物理キーをかざす | フィッシングに強い。キーの配布・紛失時の対応が必要 |

### 3.3 パスワードレス

| 方式 | 内容 | 注意点 |
|---|---|---|
| パスキー（FIDO2 / WebAuthn） | 端末に保存した秘密鍵で認証する。端末のロック解除（指紋・顔・PIN）と組み合わせて使う | フィッシングに強い。サイトのドメインに紐づくため偽サイトでは使えない。共用端末での運用に工夫が必要 |
| ワンタイムコード・マジックリンク | パスワードの代わりに、メール・SMS で送ったコードやリンクでログインする | 安全性はメール・SMS の安全性に依存する。単独では1要素 |

### 3.4 フェデレーション（SSO）・ソーシャルログイン

| 方式 | 内容 | 注意点 |
|---|---|---|
| SAML 2.0 | XML ベースの SSO 標準。企業・病院向けの IdP（Microsoft Entra ID 等）で広く使われる | IdP ごとに証明書・メタデータの設定と、証明書の更新が必要 |
| OpenID Connect（OIDC） | OAuth 2.0 をベースにした SSO 標準。Web・モバイルアプリで扱いやすい | IdP ごとにクライアント ID・シークレットの管理が必要 |
| ソーシャルログイン | 個人の Google アカウント・Microsoft アカウント等でログインする（中身は OIDC 等） | 本人確認・MFA の設定・退職時の無効化を、サービス事業者も医療機関も管理できない |

フェデレーションでは、パスワードの管理や MFA は IdP 側で行う。医療機関が Entra ID 等で MFA を必須にしていれば、サービス側で MFA を持たなくても MFA の要件を満たせる。

### 3.5 クライアント証明書（mTLS）

- 端末に電子証明書を入れ、TLS の接続時に端末を認証する。「所持」の要素になる
- 許可した端末からしか接続できないため、端末を限定したい場合に向く
- 証明書の発行・配布・失効・更新の運用が必要。利用者個人ではなく端末を認証する点に注意する
- 医療分野では、HPKI（保健医療福祉分野の公開鍵基盤）の IC カードを使う方法もある

### 3.6 補助的な対策

単独では認証方式にならないが、上記と組み合わせて使う。

| 対策 | 内容 |
|---|---|
| 送信元 IP の制限 | 医療機関の固定 IP からのみログインを許可する。固定 IP を持たない施設もある |
| リスクベース認証 | いつもと違う場所・端末からのログインや、漏えい済みパスワードの使用を検知して、追加の認証を求めたりブロックしたりする |
| セッション管理 | 一定時間操作がなければログアウトする。共用端末での放置対策 |

## 4. 比較表

凡例: ◎ 優れている ／ ○ 十分 ／ △ 注意が必要 ／ × 不向き

| 方式 | 要素 | フィッシング耐性 | 利用者の手間 | 導入・運用の負担 | 単独で MFA になるか | 主な弱点 |
|---|---|---|---|---|---|---|
| ID・パスワードのみ | 知識 | × | ○ | ◎ | × | 漏えい・使い回し・総当たり |
| パスワード + SMS コード | 知識 + 所持 | △ | △ | ○（送信費用あり） | ○ | SIM スワップ、フィッシング |
| パスワード + メールコード | 知識 + 所持 | △ | △ | ◎ | △（メールの管理状態による） | メールアカウントの乗っ取り |
| パスワード + TOTP | 知識 + 所持 | △ | △ | ◎ | ○ | フィッシング、スマートフォンの機種変更時の再登録 |
| パスワード + プッシュ通知 | 知識 + 所持 | △ | ○ | △（専用アプリが必要） | ○ | MFA 疲労攻撃 |
| FIDO2 セキュリティキー | 所持（+ PIN・生体） | ◎ | ○ | △（キーの配布・紛失対応） | ○ | 紛失、配布費用 |
| パスキー | 所持 + 生体・PIN | ◎ | ◎ | ○ | ○ | 共用端末での運用、端末紛失時の復旧手順 |
| メール・SMS のワンタイムコードのみ | 所持 | △ | ○ | ◎ | × | メール・SMS の安全性に依存 |
| SAML / OIDC フェデレーション | IdP に依存 | IdP に依存 | ◎（SSO） | △（施設ごとに IdP 設定） | IdP の MFA 設定による | IdP を持たない小規模施設には使えない |
| ソーシャルログイン（個人アカウント） | 個人の設定に依存 | 個人の設定に依存 | ◎ | ○ | 保証できない | 本人確認・退職時の無効化ができない |
| クライアント証明書 | 所持（端末） | ◎ | ◎（導入後） | ×（証明書の配布・失効） | ×（パスワード等と併用して MFA） | 端末の認証であり利用者個人の認証ではない |

## 5. 医療情報システムで採用する際の考慮点

### 5.1 ガイドラインの要件

| 項目 | 内容 |
|---|---|
| MFA | 厚生労働省ガイドライン第7.0版では、クライアント端末のアプリケーションログインにも MFA が求められる。令和9年度時点（令和9年4月1日時点）で稼働が想定されるシステムの新規導入・更改時に原則採用する。困難な場合は、直近の次期更改までの経過措置がある |
| パスワード | 同版システム運用編14章による。二要素認証を併用する場合は8桁以上、併用しない場合は13桁以上の英数字混在（大文字・小文字は問わない）。定期変更は不要。異なる医療情報システム間での使い回しは禁止 |
| アカウントロック | 一定回数の認証失敗で、一定時間ログインできないようにする |
| 利用者の特定 | 誰が・いつ・どの患者の画像を見たかを記録できるよう、個人単位のアカウントにする（[U08](./requirements.md#u08)） |

条文の詳細は実装時に公式資料で確認する。

### 5.2 方式ごとの注意点

| 観点 | 内容 |
|---|---|
| ソーシャルログイン | 個人の Google・Microsoft アカウントは、医療機関が退職者のアカウントを止められず、MFA の設定も強制できない。医療情報システムの利用者認証には向かない |
| 医療機関の IdP 連携 | 医療機関が Entra ID・Google Workspace を職員の ID 管理に使っている場合は、SAML / OIDC 連携が有力。退職時に医療機関側でアカウントを止めれば、本サービスにもログインできなくなる |
| IdP を持たない施設 | 小規模クリニックなどは IdP を持たないことが多い。サービス独自のアカウント + MFA も並行して用意する |
| 共用端末 | 読影室・検査室の PC は複数人で共用することが多い。端末に紐づくパスキー（指紋・顔）は使いにくいため、TOTP・FIDO2 セキュリティキー・IC カード等を検討する |
| SMS・メール | SMS は医療機関の職員が業務用の携帯電話を持たない場合に使えない。メールは乗っ取りのリスクがあるため、2要素目としての採用は慎重に判断する |
| 端末の限定 | 院外からの閲覧を許可端末に限りたい場合は、クライアント証明書を利用者認証（パスワード + MFA）と併用する |

### 5.3 本サービスでの推奨（たたき台）

| 利用者 | 推奨する方式 |
|---|---|
| IdP を持つ施設（病院等） | SAML / OIDC フェデレーション。MFA は施設の IdP で必須にしてもらう（契約・責任分界表に明記する） |
| IdP を持たない施設（クリニック等） | サービス独自のアカウント + TOTP。パスキーを選択肢として提供する |
| 自社の運用者 | サービス独自のアカウント + パスキーまたは FIDO2 セキュリティキー（フィッシング耐性を重視） |

決定は要件定義の [U08](./requirements.md#u08) で行う。

## 6. Amazon Cognito での実現方法

Cognito ユーザープールには機能プラン（Lite / Essentials / Plus）があり、プランによって使える機能が異なる。新規作成時の既定は Essentials。

| 方式 | Cognito での実現方法 | 必要なプラン |
|---|---|---|
| ID・パスワード | ユーザープールのローカルユーザー。パスワードポリシー（最小文字数・文字種）を設定できる | Lite 以上 |
| SMS コード・TOTP による MFA | ユーザープールの MFA 設定 | Lite 以上 |
| メールコードによる MFA | ユーザープールの MFA 設定 | Essentials 以上 |
| パスキー | パスキーによるサインイン（1要素目） | Essentials 以上 |
| メール・SMS のワンタイムコードによるパスワードレス | パスワードレスサインイン | Essentials 以上 |
| SAML / OIDC フェデレーション | 外部 IdP として登録する。Microsoft Entra ID は SAML または OIDC で連携する | Lite 以上（フェデレーションユーザーは別途 MAU 課金） |
| ソーシャルログイン | Google・Facebook・Amazon・Apple を組み込みの IdP として登録できる | Lite 以上 |
| リスクベース認証・漏えいパスワードの検知 | 脅威保護（旧 高度なセキュリティ機能） | Plus |
| クライアント証明書（mTLS） | Cognito には機能がない。ALB・API Gateway の mTLS で実現する | — |

**実装時の注意点**

- フェデレーションユーザーには Cognito の MFA は適用されない。MFA は外部 IdP 側で必須にする
- Cognito のパスワードポリシーには定期変更を強制する設定がない。ガイドラインの「定期変更は不要」と合う
- Cognito は認証の失敗が続くとログインを一時的に止める。ガイドラインが求める失敗回数・ロック時間を満たすか確認し、足りなければ Lambda トリガー等で補う
- パスキーとパスワードレスを使う場合は Essentials 以上が必要。漏えいパスワードの検知や不審なログインのブロックまで使う場合は Plus にする
