## 1. この資料について

- 現時点で Windows EC2 の Terraform 実装はない。Windows EC2 を導入する場合のたたき台とする
- 方針の決定は要件定義の [U17 運用手順・変更管理・パッチ適用](./requirements.md#u17) で行う
- 決定後、Terraform で実装したもの（SSM Maintenance Window・Patch Baseline 等）は [infra/README.md](../infra/README.md) に記載する

## 2. 対象

AWS 固有のドライバー（ENA・NVMe・PV）は Windows Update では配信されない。Windows 本体のパッチとは別に更新する。

| 種別 | 用途 | 更新手段 |
|---|---|---|
| ENA ドライバー | Nitro 系インスタンスのネットワーク | SSM Distributor `AwsEnaNetworkDriver` |
| AWS NVMe ドライバー | Nitro 系インスタンスの EBS・インスタンスストア | SSM Distributor `AWSNVMe` |
| AWS PV ドライバー | 旧 Xen 系インスタンス（T2・M4 等） | SSM Distributor `AWSPVDriver` |
| EC2Launch v2 | 起動時の初期設定 | SSM Distributor `AWSEC2Launch-Agent` |
| SSM Agent | Session Manager・Run Command | `AWS-UpdateSSMAgent` |
| CloudWatch Agent | ログ・メトリクス収集 | SSM Distributor `AmazonCloudWatchAgent` |
| GPU ドライバー（NVIDIA 等） | G 系インスタンスを使う場合 | AWS 提供の S3 バケット、またはベンダー提供版 |
| Windows 本体・一般ドライバー | Microsoft 配信分 | SSM Patch Manager `AWS-RunPatchBaseline` |

## 3. 更新方式

| 方式 | 内容 | 向いている対象 |
|---|---|---|
| A ゴールデン AMI（第一候補） | EC2 Image Builder のパイプラインで、AWS 提供の最新 Windows AMI（毎月 Patch Tuesday 後に更新、AWS ドライバーを含む）を元に自社 AMI を毎月作る。検証後にインスタンスを入れ替える | 状態を持たないサーバー。切り戻しは旧 AMI に戻すだけで済み、構成のドリフトも起きない |
| B インプレース更新 | SSM Maintenance Window で、稼働中のインスタンスにドライバーとパッチを適用する | 入れ替えが難しい、状態を持つサーバー |
| C 緊急・世代移行 | Automation ランブック `AWSSupport-UpgradeWindowsAWSDrivers` で、停止したインスタンスにもオフラインで適用する | Xen 系から Nitro 系への移行、ドライバー不具合で起動しない場合 |

## 4. 手順（方式 B）

### 4.1 実施タイミング

| 環境 | 実施タイミング | 目的 |
|---|---|---|
| dev | 随時 | 最新版での動作確認 |
| stg | prod の定期メンテナンスより前 | prod と同じ手順の予行。切り戻し（[5 章](#5-切り戻し手順方式-b)）の所要時間もここで測る |
| prod | 定期メンテナンスの時間帯 | 本番適用。切り戻しまで含めて時間内に終える |

### 4.2 定期メンテナンス内の作業

prod では、切り戻しに必要な時間を残して「切り戻し判断の期限」を決めておく（例：終了時刻 −（stg で測った切り戻しの所要時間 + 余裕））。

| 順序 | 作業 | 使う機能・内容 |
|---|---|---|
| 1 | 業務の停止 | モダリティ・院内ゲートウェイからの DICOM 送信を止め、PACS 関連サービスを停止する |
| 2 | 事前バックアップ | `AWS-CreateImage`（`NoReboot=false`：インスタンスを一度停止して取得し、ファイルシステムの整合性を保つ）。AMI が `available` になったことを確認してから次に進む |
| 3 | 更新前の状態を記録 | 適用済みの KB 一覧、ドライバー・エージェントのバージョン（SSM Inventory または Run Command で取得） |
| 4 | AWS ドライバー・エージェントの更新 | Run Command `AWS-ConfigureAWSPackage`（`version` を指定して固定する） |
| 5 | Windows パッチの適用 | Run Command `AWS-RunPatchBaseline` |
| 6 | 再起動と正常性確認 | 「[5.1 切り戻しの判断基準](#51-切り戻しの判断基準)」の項目を確認する |
| 7 | 判定 | 問題なし → 業務を再開する。問題あり、または判断の期限を過ぎても解決しない → [5 章](#5-切り戻し手順方式-b)の切り戻しを行う |

業務（DICOM 受信）の再開は、判定で「問題なし」となってから行う。再開後に切り戻すと、バックアップ以降に受信したデータが失われるため。

### 4.3 環境ごとの適用

| 環境 | 適用するバージョン | 承認 |
|---|---|---|
| dev | 最新版 | 不要 |
| stg | dev で問題がなかった版 | 不要 |
| prod | stg で検証した版（`version` を固定する） | 変更作成者以外の承認者が承認する（アプリの本番デプロイと同じ職務分離） |

### 4.4 記録として残すもの

- Maintenance Window の実行履歴
- Run Command の出力（S3 または CloudWatch Logs に出力する）
- CloudTrail（誰がいつ実行したか）
- 適用したドライバー・パッチのバージョンと承認者
- 事前バックアップの AMI ID・スナップショット ID
- 切り戻しを行った場合は、その判断理由・実施者・使った手段・結果

## 5. 切り戻し手順（方式 B）

### 5.1 切り戻しの判断基準

次のどれかに当てはまり、判断の期限までに解決できない場合は切り戻す。

| # | 確認項目 | 確認方法 |
|---|---|---|
| 1 | インスタンスが起動しているか | EC2 ステータスチェック（システム・インスタンスの両方） |
| 2 | 管理用の接続ができるか | SSM で接続できるか（Fleet Manager のマネージドノードが Online か） |
| 3 | アプリが動いているか | ALB のターゲットヘルスチェック、PACS 関連サービスの起動状態 |
| 4 | 業務が行えるか | テスト用 DICOM の送受信、ビューアでの画像表示 |
| 5 | ログに異常がないか | Windows イベントログ（System・Application）に新しいエラーがないか |

### 5.2 切り戻しの手段

基本はルートボリュームの置換（手段 1）とする。ENA ドライバーの不具合では SSM で接続できなくなることが多く、個別の戻しは使えない場合があるため。

| 手段 | 内容 | 使う場面 | 影響 |
|---|---|---|---|
| 1 ルートボリュームの置換（基本） | 事前バックアップのルートボリュームのスナップショットから、C ドライブだけを元に戻す | 原因が特定できない、SSM で接続できない、起動しない | インスタンス ID・プライベート IP・ENI・IAM ロール・データボリュームはそのまま。ALB のターゲットや DNS の変更は不要 |
| 2 個別の戻し | ドライバーは前のバージョンを指定して再インストール、パッチは KB をアンインストールする | 原因の更新が特定でき、SSM で接続できる | 再起動のみ。KB によってはアンインストールできないため、その場合は手段 1 に進む |
| 3 AMI から別インスタンスを起動 | 事前バックアップの AMI から新しいインスタンスを起動し、入れ替える | 手段 1 が失敗した場合 | インスタンス ID が変わる。ALB ターゲットの登録し直しと Terraform の state 調整が必要 |

### 5.3 手段 1：ルートボリュームの置換

1. 事前バックアップの AMI から、ルートボリューム（`/dev/sda1`）のスナップショット ID を確認する

   ```sh
   aws ec2 describe-images --image-ids <AMI ID> \
     --query "Images[0].BlockDeviceMappings[?DeviceName=='/dev/sda1'].Ebs.SnapshotId"
   ```

2. ルートボリュームの置換タスクを作成する。インスタンスは自動で再起動する。`--delete-replaced-root-volume` は付けない（置換前のボリュームを残し、後で原因を調査する）

   ```sh
   aws ec2 create-replace-root-volume-task \
     --instance-id <インスタンス ID> --snapshot-id <スナップショット ID>
   ```

3. タスクが `succeeded` になるまで待つ

   ```sh
   aws ec2 describe-replace-root-volume-tasks \
     --filters Name=instance-id,Values=<インスタンス ID>
   ```

4. 「[5.1 切り戻しの判断基準](#51-切り戻しの判断基準)」の項目を確認し、ドライバー・KB が更新前の状態（[4.2](#42-定期メンテナンス内の作業) の順序 3 で記録したもの）に戻ったことを確認する
5. 業務を再開する
6. `terraform plan` を実行し、意図しない差分がないことを確認する

置換は、インスタンスの状態が `running` のときだけ実行できる。OS が起動しなくても、EC2 上の状態が `running` であれば実行できる。

データボリュームは元に戻さない。更新はデータボリュームを変更しないため。データボリュームも戻す必要がある場合は、インスタンスを停止し、スナップショットから作ったボリュームと付け替える。

### 5.4 手段 2：個別の戻し

SSM の Run Command で実行する。

| 対象 | 戻し方 |
|---|---|
| AWS ドライバー・エージェント | `AWS-ConfigureAWSPackage` で `action=Install`・`version=<更新前のバージョン>` を指定する |
| Windows パッチ | `wusa.exe /uninstall /kb:<KB 番号> /quiet /norestart` を実行して再起動する。アンインストールできない KB の場合は手段 1 に進む |

戻したパッチは、原因が解消するまで Patch Baseline の除外（`RejectedPatches`）に登録し、次の定期メンテナンスで再適用されないようにする。

### 5.5 切り戻し後の対応

- 切り戻しの記録を残す（[4.4](#44-記録として残すもの)）
- 置換前のルートボリュームから原因を調査する。調査用のインスタンスに付けて、イベントログや更新履歴を確認する
- 調査が終わったら、置換前のボリュームを削除する
- 定期メンテナンスの時間を延長する場合は、医療機関に連絡する（連絡の手順は U17 の運用手順書で決める）

### 5.6 事前バックアップの保持と削除

- 事前バックアップの AMI は、次回の定期メンテナンスで新しいバックアップを取るまで保持する
- 更新後に時間がたってから問題が見つかった場合も、ルートボリュームの置換で戻せる。ただしバックアップ後に OS に入れた変更（設定変更・ログ等）は失われる
- 削除するときは、AMI の登録解除と、関連するスナップショットの削除の両方を行う。AMI の登録を解除しても、スナップショットは自動では消えない
- AMI とスナップショットには、取得日と目的（例：`Purpose=pre-patch-backup`）のタグを付ける。KMS で暗号化されていることを確認する

## 6. 注意事項

- **事前バックアップは必須**。ドライバー更新に失敗すると起動しない、または通信できなくなり、SSM で操作できなくなる。事前のスナップショットが唯一の復旧手段になる場合がある
- **切り戻しは stg で事前に試す**。所要時間を測り、prod の切り戻し判断の期限（[4.2](#42-定期メンテナンス内の作業)）を決める根拠にする
- **復元したボリュームは、最初の読み込みが遅い**。スナップショットから作った EBS ボリュームは、各ブロックへの初回アクセス時に S3 から読み込まれるため。業務再開前に、主要な処理の応答時間を確認する
- **切り戻しに必要な権限を事前に確認する**。作業者の権限セットで `ec2:CreateReplaceRootVolumeTask` 等が実行できることを、stg で確認しておく
- **ENA ドライバーの更新中は通信が数秒切れる**。定期メンテナンスの時間帯に行い、モダリティからの DICOM 送信を止める
- **インスタンスタイプを Nitro 系に変える前に、ENA と NVMe のドライバーを確認する**。入っていないと起動に失敗する。AWS 公式の事前チェック手順に従う
- **バージョンを見える化する**。SSM Inventory でドライバーとエージェントのバージョンを集め、環境間の差分を把握する
- **リリース情報を追う**。ENA・NVMe・EC2Launch のバージョン履歴ページを定期的に確認し、AWS Health の通知を受け取る
- **PACS 関連ソフトのベンダーがサポートするバージョンを確認する**。ベンダーが動作を保証する OS パッチ・ドライバーのバージョンを指定している場合は、承認を得たバージョンに固定する

## 7. 3省2ガイドラインとの対応

| 観点 | 対応 |
|---|---|
| 脆弱性対策（パッチの計画的な適用） | 定期更新（方式 A または B）と、緊急適用の基準を定める |
| 変更管理の記録 | 「[4.4 記録として残すもの](#44-記録として残すもの)」を保存する |
| 監査証跡の改ざん防止 | CloudTrail は Object Lock 付きのバケットに保存済み（[infra/README.md](../infra/README.md#注意事項)） |
| バックアップ・復旧 | 適用前に AMI を取得し、切り戻し手順（[5 章](#5-切り戻し手順方式-b)）を stg で事前に試す |
| 保存データの暗号化 | 事前バックアップの AMI・スナップショットは KMS で暗号化する |

> 該当する条文は、厚生労働省ガイドライン第7.0版のシステム運用編で要確認。

## 8. 未決事項

[U17](./requirements.md#u17) で決める。

| # | 論点 | 暫定の推奨 |
